<p>分配的本质是做匹配：账号权重高的配好地址，地区敏感的配本地地址，多店同人的配不同 ASN。这篇给出一张分配矩阵，再讲配置时怎么把分配落到设备与浏览器上，然后是串号的预防与排查。</p>
<h2>一、分配矩阵怎么排</h2>
<p>按两个维度排：账号重要程度、地区敏感度。重要且敏感，配独享静态且地区精确；重要不敏感，配独享静态即可；不重要但敏感，配地区正确的共享段；都不敏感，机房段也能用。</p>
<p>这张矩阵的价值在于把有限预算花在刀刃上。全部买最贵的没有必要，全部买最便宜的一定出问题。</p>

<h2>二、配置落地</h2>
<p>分配结果要落到三个地方：路由器或服务器的出口规则、浏览器环境的代理设置、账号台账。三处一致，才算配置完成。</p>
<p>最容易出问题的是第二处。浏览器环境里如果开了“自动检测代理”，可能绕过你设的规则；如果用了插件，插件更新后设置可能被重置。配完要重新核对一次。</p>
<h3>串号的预防</h3>
<p>预防靠制度：每个操作者只接触自己负责的账号与环境，环境命名与账号编号一致，配置改动要留记录。靠记忆防串号，迟早出事。</p>
<h2>三、串号之后怎么查</h2>
<p>第一步，确认哪几个账号出现同类异常。第二步，查这些账号的出口记录，看是否有交叉。第三步，查同段地址上是否还有其他账号。第四步，查操作时间是否高度重合。</p>
<p>四步下来，串号路径基本能画出来。发现串号后，先停用相关地址，再逐个换到干净段，别一次性全换，否则无法判断是哪一步起了作用。</p>

<h2>四、长期维护</h2>
<p>每月复核一次分配矩阵，账号增减后及时调整。地址评分上升的，从关键组调到辅助组，别让坏段拖累重要账号。</p>
<p>台账每月对一次账：地址数、账号数、在用与闲置。数字对不上就查，问题往往在细节里。</p>
<h2>四、地区匹配的细节</h2>
<p>地址归属地要与店铺注册地一致，城市尽量一致。做不到时，至少同省或同州。跨州频繁变动，比固定在一个异地城市更容易触发核验。</p>
<p>时区是配套项。地址在纽约，系统时区却是北京时间，这个矛盾很显眼。把时区、语言、货币显示都对齐，才算地区匹配做完。</p>
<h2>五、分配后的复盘</h2>
<p>每月复盘一次：哪些账号验证频率上升、哪些地址评分变差、分配是否需要调整。复盘要有记录，否则每次都在重复同样的判断。</p>
<p>复盘结论落到调整动作上：调级别、换地址、改环境。只复盘不调整，等于没做。</p>
<h2>常见问答</h2>
<h3>一个账号换地址会被发现吗？</h3>
<p>答：会看到登录地变化。偶尔一次问题不大，频繁变化验证会变多。</p>
<h3>可以按店铺类目分配地址吗？</h3>
<p>答：可以，同地区同类目集中管理更省事。但同人运营的多店不要放同一段。</p>
<h3>共用地址最多几个店？</h3>
<p>答：建议不超过两个，且这两个店之间本来没有关联。</p>
<h3>分配好之后还要调吗？</h3>
<p>答：要。账号权重会变，地址质量会变，分配也该跟着调整。</p>
